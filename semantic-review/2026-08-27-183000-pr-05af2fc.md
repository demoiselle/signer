# Corrige hashAlgorithm incorreto no SignaturePolicyIdentifier

Este commit separa duas responsabilidades que estavam mescladas na classe `SignaturePolicy`: o algoritmo de hash usado para proteger o arquivo `.der` da política (`signPolicyHashAlg`) e o algoritmo de hash usado na assinatura do documento (ex: SHA-512 ao assinar com SHA512withRSA). O antigo `prepareAlgAndLength()` sobrescrevia `signPolicyHashAlg` com o OID do hash de assinatura do documento, fazendo com que o atributo SignaturePolicyIdentifier declarasse o algoritmo errado. A correção introduz um novo campo `signatureAlgorithmHashOID` para transportar o OID do hash do documento separadamente, atualiza o `MessageDigest` para lê-lo, e adiciona uma validação no verificador que detecta inconsistências OID/tamanho-do-hash em assinaturas existentes.

Atenção: a tabela `getExpectedHashSize` no `CAdESChecker` omite SHA-224 (28 bytes), que o codebase referencia em `AlgorithmNames`; encontrar um hash de política SHA-224 produzirá um falso warning (provável). O `catch (Exception)` genérico em `validateSignaturePolicyHash` registra no logger mas não grava em `signatureInfo`, criando um caminho de falha silenciosa para consumidores downstream (confirmado).

**Veredito**: APROVADO

## Visão geral

A causa raiz era um único campo mutável `AlgorithmIdentifier` servindo a dois propósitos. A correção adiciona um campo `String` dedicado para o OID do hash do documento, remove todo código que mutava `signPolicyHashAlg`, e atualiza o único consumidor (`MessageDigest`) para ler o novo campo com fallback para compatibilidade retroativa.

O `CAdESChecker` ganha uma verificação estrutural que faz parse do ASN.1 bruto do atributo `SignaturePolicyIdentifier` e compara o tamanho esperado de saída do algoritmo de hash declarado com os bytes reais do hash. Isso detecta exatamente a classe de bug sendo corrigida (algoritmo diz SHA-256 mas o hash tem 64 bytes) sem tentar verificação completa do hash contra o arquivo da política. O mapeamento OID-para-tamanho está incompleto (falta SHA-224) e o tratamento de exceção tem uma assimetria com o restante do método.

A suíte de testes cobre a condição de regressão e o comportamento preservado nos três branches do `prepareAlgAndLength()`, mas não há teste para o próprio `validateSignaturePolicyHash`.

<summary>Detalhes técnicos</summary>

## Separação dos OIDs de hash da política e do documento

O código anterior usava um único objeto mutável `AlgorithmIdentifier` (`signPolicyHashAlg`) para ambos os propósitos. Como `AlgorithmIdentifier` é um POJO mutável, a mutação em `prepareAlgAndLength()` se propagava para qualquer consumidor downstream que lesse `signPolicyHashAlg` esperando o hash original do arquivo da política. O novo design usa uma `String` simples para o OID do hash do documento, eliminando o problema de aliasing. Os três pontos de chamada em `prepareAlgAndLength()` (branch if, branch else, fallback) o configuram simetricamente.

## Validação de tamanho do hash no verificador

`validateSignaturePolicyHash` percorre manualmente a estrutura ASN.1 do `SignaturePolicyId`. O parsing é linear e bem protegido por retornos antecipados em caso de estrutura inesperada.

O helper `getExpectedHashSize` codifica quatro OIDs (SHA-1, SHA-256, SHA-384, SHA-512). SHA-224 (`2.16.840.1.101.3.4.2.4`, 28 bytes) está ausente apesar de aparecer em `AlgorithmNames`. Um hash de política SHA-224 válido dispara `POLICY_HASH_UNKNOWN_ALGORITHM` — um falso warning, não um falso erro, portanto o impacto é baixo mas a correção é trivial:

```java
if (oid.equals(org.bouncycastle.asn1.nist.NISTObjectIdentifiers.id_sha224)) return 28;
```

O `catch (Exception e)` genérico no final registra no logger mas não adiciona mensagem em `signatureInfo.getValidatorWarnins()`. Isso cria uma assimetria: o caminho de algoritmo desconhecido registra corretamente tanto no logger quanto em signatureInfo, mas o caminho de falha de parsing só atinge o logger. Código downstream que exibe resultados de validação para usuários perderá silenciosamente falhas de parsing ASN.1.

## Lacunas de cobertura de testes

Ambas as classes de teste usam reflexão para injetar uma `SignaturePolicy` customizada e invocar `prepareAlgAndLength()` diretamente, cobrindo a regressão e os três caminhos principais de código. Não testados: `validateSignaturePolicyHash` com um `Attribute` sintético contendo hash com tamanho inconsistente, e o caminho de fallback do `MessageDigest` quando `signatureAlgorithmHashOID` é null.
